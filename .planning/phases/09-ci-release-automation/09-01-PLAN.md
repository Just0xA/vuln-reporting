<objective>
Ship `.github/workflows/release.yml` — the GitHub Actions workflow that, on every `v*` tag push (or manual `workflow_dispatch`), builds the slim release tarball, computes a SHA256 sidecar, detects prerelease suffixes, and publishes both assets to a GitHub Release.

Purpose: Eliminate the manual release-cutting step for the v1.2 operator-deployable suite. Maintainer's only action is pushing a tag; everything else (tarball construction, checksum, prerelease flag, asset upload, Release creation) is automated and reproducible.

Output: A single new file `.github/workflows/release.yml` with one job (`release`) running on `ubuntu-latest`. Plan 09-02 will add the tarball-content assertion step into the same job between "build tarball" and "upload assets".

  <action>
    Create `.github/workflows/release.yml` as a single-job workflow. The job is `release`, runs on `ubuntu-latest`. Plan 09-02 will insert an assertion step between the "Build tarball" and "Upload to GitHub Release" steps; leave the file shaped so that insertion is clean (one logical step per concern, named explicitly).

    Required workflow shape (directive — implement in idiomatic YAML, not a literal paste):

    1. **`name:`** — `Release`.

    2. **`on:`** — two triggers:
       - `push: tags: ['v*']` (CI-01)
       - `workflow_dispatch:` with one input `version` (`type: string`, `required: true`, `description: 'Tag to release (e.g. v1.2.0)'`) — CI-02.

    3. **Top-level `permissions:`** — `contents: write` only. No other scopes. This is CI-07 and the workflow MUST NOT rely on repo-level default token permissions.

    4. **`jobs.release:`** — single job, `runs-on: ubuntu-latest`.

    5. **Step: Checkout** — `uses: actions/checkout@v6`, `with: fetch-depth: 0`. Full history is required so `git archive <ref>` resolves both tag-push and manual-dispatch refs against the committed tree (the export-ignore rules in `.gitattributes` only apply to committed content).

    6. **Step: Resolve version** — a `run:` step that sets a `VERSION` step output. Logic:
       - If `github.event_name == 'workflow_dispatch'`: `VERSION="${{ inputs.version }}"`.
       - Else (tag push): `VERSION="${{ github.ref_name }}"`.
       - Validate the value matches `^v[0-9]+\.[0-9]+\.[0-9]+(-(rc|beta|alpha)[0-9.]*)?$` via a `grep -E` regex; exit 1 with a clear error if not. This catches typos in manual-dispatch input early.
       - Export to `$GITHUB_OUTPUT` as `version=$VERSION`.
       - Step `id: version`.

    7. **Step: Detect prerelease** — a `run:` step that inspects `${{ steps.version.outputs.version }}` for the substrings `-rc`, `-beta`, or `-alpha` (case-sensitive). Use a shell `case` or `grep -E '\-(rc|beta|alpha)'`. Write `prerelease=true` or `prerelease=false` to `$GITHUB_OUTPUT`. Step `id: prerelease`. CI-05.

    8. **Step: Build slim tarball** — a `run:` step that:
       - Computes `VERSION=${{ steps.version.outputs.version }}`.
       - Runs `git archive --format=tar.gz --prefix=vuln-reporting-${VERSION}/ -o vuln-reporting-${VERSION}-slim.tar.gz ${VERSION}` (CI-03). Passing the version as the ref guarantees the archive is built from the tagged commit, not from `HEAD` (which matters on `workflow_dispatch` re-runs against historical tags).
       - The `-slim` suffix is mandatory: it differentiates this asset from GitHub's auto-generated source tarball that always accompanies a Release.
       - Does NOT pass any path arguments — relying entirely on `.gitattributes` `export-ignore` to define exclusions. Duplicating exclusions in the workflow is a drift hazard; Plan 09-02 is the safety net.

    9. **Step: Compute SHA256 sidecar** — a `run:` step:
       - `sha256sum vuln-reporting-${VERSION}-slim.tar.gz > vuln-reporting-${VERSION}-slim.tar.gz.sha256` (CI-04).
       - The sidecar format is the GNU `sha256sum` default (`<hex>  <filename>`), which downstream Phase 10 `update_from_github.sh --check` can verify with `sha256sum -c`.

    10. **(Insertion point for Plan 09-02 — tarball-content assertion goes HERE.)** Leave a comment line `# Tarball-content assertion step inserted by Plan 09-02` so the executor for the next plan has an unambiguous landing site.

    11. **Step: Upload to GitHub Release** — `uses: softprops/action-gh-release@v3`. Inputs:
        - `tag_name: ${{ steps.version.outputs.version }}` (lets `workflow_dispatch` runs target an existing tag).
        - `name: ${{ steps.version.outputs.version }}` (Release title = tag).
        - `prerelease: ${{ steps.prerelease.outputs.prerelease == 'true' }}` — note YAML truthiness: `softprops/action-gh-release@v3` accepts boolean inputs as strings; the comparison expression evaluates to `true`/`false`.
        - `files: |` (literal block scalar with two lines)
          ```
          vuln-reporting-${{ steps.version.outputs.version }}-slim.tar.gz
          vuln-reporting-${{ steps.version.outputs.version }}-slim.tar.gz.sha256
          ```
        - `fail_on_unmatched_files: true` — if either asset is missing, fail the workflow loudly rather than publish a half-complete release.
        - No `body:` or `body_path:` for v1.2 — the auto-generated changelog is sufficient. (Adding release notes is a deferred-ideas concern, not in scope.)

    12. **`env:` block at the job level** — set `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` so any future `gh` CLI invocation in the same job inherits auth without re-declaration. (`softprops/action-gh-release@v3` reads `GITHUB_TOKEN` automatically; this is forward-looking, not load-bearing today. Keep it because it costs one line and saves a future surprise.)

    Style:
    - YAML 2-space indentation, no tabs.
    - Use `${{ steps.version.outputs.version }}` (not raw `${{ github.ref_name }}`) everywhere downstream of step 6 so the manual-dispatch path is symmetric with the tag-push path.
    - Step `name:` strings are human-readable sentences ("Build slim tarball" not "build_tarball").
    - Do NOT add `if:` guards on individual steps — the only branching needed (event source) is fully encapsulated in step 6.
    - Do NOT introduce `matrix:` — single OS, single Python version (there is no Python execution in this workflow; `git archive` is pure git).

    Do NOT modify `.gitattributes`, `.gitignore`, or any project source in this task — the workflow file is the only deliverable.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Maintainer push → GitHub Actions runner | Tag push or `workflow_dispatch` triggers an ephemeral runner with `GITHUB_TOKEN`. |
| Runner → GitHub Releases API | Token must be scoped to `contents: write` only — no broader repo access. |
| `.gitattributes` (Phase 7) → `git archive` invocation | The workflow trusts `.gitattributes` to define the tarball boundary. Plan 09-02's assertion is the runtime check that this trust is well-placed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Elevation of Privilege | Default `GITHUB_TOKEN` scopes leaking to release job | mitigate | Explicit `permissions: contents: write` at top level overrides any broader default. |
| T-09-02 | Tampering | Unpinned action version pulls a malicious tag | mitigate | Pin to verified major versions (`actions/checkout@v6`, `softprops/action-gh-release@v3`) confirmed 2026-05-19. Major-version pinning over SHA pinning is a deliberate tradeoff: Dependabot can auto-bump majors; SHA pins fail silently when actions ship security patches. |
| T-09-03 | Tampering | Manual `workflow_dispatch` version input contains shell injection | mitigate | Regex validation in step 6 rejects any value not matching `^v[0-9]+\.[0-9]+\.[0-9]+(-(rc\|beta\|alpha)[0-9.]*)?$`. The value is then passed via `$GITHUB_OUTPUT` and consumed by `git archive` which treats it as a ref, not a shell expression. |
| T-09-04 | Information Disclosure | Tarball ships secrets or dev-only files | transfer | Plan 09-02 (CI-06) owns this gate — the assertion step fails the build before upload. |
</threat_model>
