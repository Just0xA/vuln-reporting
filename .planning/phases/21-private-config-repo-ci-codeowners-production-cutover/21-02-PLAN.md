<objective>
Author the reference CI gate for the PRIVATE config repo (D-06/D-07): on every PR it fetches a
PINNED `vuln-reporting` slim release tarball, verifies the `.sha256` sidecar, installs
`requirements.txt`, and runs schema validation + `run_all.py --dry-run` against the merged
effective config — a non-zero exit blocks merge. It publishes the names+owner delivery matrix
as a PR artifact for reviewers.

Critical: the CI gate is **pre-auth (Hard Rule 1)** — no Tenable/SMTP credentials in CI. Because
`_dry_run` currently returns 1 when `_REQUIRED_ENV_VARS` are missing (run_all.py:441-447), this
plan MUST make the gate fail on CONFIG errors, not on missing creds — by supplying placeholder
env values in the CI step so the env-presence check passes and the real config validation is what
gates the merge.

Purpose: CONF-04 SC2 — CI blocks a bad merge before it reaches production.
Output: `deploy/config-repo/ci.yml.example` + `deploy/config-repo/README.md`.

**Repo target:** These files are authored in the PUBLIC app repo under `deploy/config-repo/` as
clearly-labelled REFERENCE artifacts (`.example` suffix + README) for the operator to place into
the PRIVATE config repo at provisioning. They are NOT the private repo's live CI — they are the
committed template. No real config, no real handles (Hard Rule 2 / D-02).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PR author → config repo | Untrusted config change enters via PR; CI + CODEOWNERS are the gate before it can reach production |
| app-repo release asset → CI runner | CI downloads a slim tarball over the network and executes its code (`run_all.py`) — supply-chain surface |
| CI environment → secrets | CI runs pre-auth; no real Tenable/SMTP creds should ever be present |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-05 | Tampering | pinned tarball fetch | mitigate | Fetch a PINNED `PINNED_VERSION` (never `latest`) and `sha256sum -c` the `.sha256` sidecar before extraction; job fails on mismatch — the release.yml sidecar exists precisely for this downstream verification |
| T-21-06 | Elevation of Privilege | CI workflow permissions | mitigate | `permissions: contents: read` only; the gate needs no write scope; no `pull_request_target` (no secret exposure to fork PRs) |
| T-21-07 | Information Disclosure | CI credentials | mitigate | Gate is pre-auth (Hard Rule 1) — only PLACEHOLDER env is exported; no real Tenable/SMTP secrets referenced; `--dry-run` performs no live fetch |
| T-21-08 | Information Disclosure | PR matrix artifact | mitigate | The published matrix emits contact/group NAMES + owner only (never expanded recipient addresses) via the resolver side channel — safe to attach to a PR (Hard Rule 2) |
| T-21-SC | Tampering | pip install from tarball | mitigate | `requirements.txt` is pinned (Hard Rule 8, locked); no new dependency introduced by this plan; slim tarball is the reviewed app release, itself asserted config/credential-free by release.yml |
</threat_model>
