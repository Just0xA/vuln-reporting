    1. **Add helper `health_check()`** near the existing helper block:

       Takes no arguments. Returns 0 if the service is active, non-zero otherwise.
       ```
       health_check() {
         sleep 10
         systemctl is-active --quiet vuln-reports.service
       }
       ```
       The `--quiet` flag suppresses the stdout `active`/`inactive` print so the script's own output stays clean. The exit code is what we test.

    2. **Add helper `auto_rollback()`**:

       Takes one argument: `$PREV_TARGET` (the absolute path to roll back to — captured into a shell var at the top of `cmd_install`'s install pipeline, so this helper does NOT need to read `.last`).

       Body:
       ```
       auto_rollback() {
         local prev="$1"
         IN_AUTO_ROLLBACK=1                # recursion guard — see step 3 below
         log_line "AUTO-ROLLBACK: health check failed; reverting current → $prev"

         if ! atomic_swap "$prev"; then
           log_completed "failed: post-swap health check failed AND auto-rollback swap failed (manual recovery required; current may be in an inconsistent state)"
           exit 13
         fi

         # Rewrite .last to reflect the swap-back: the displaced 'current' (i.e. the broken release
         # we just rolled away from) becomes the new .last so operator can manually re-attempt.
         write_breadcrumb "$TARGET_DIR"

         if ! sudo systemctl restart vuln-reports.service; then
           log_completed "failed: post-swap health check failed AND auto-rollback restart failed (service may be down; manual recovery required)"
           exit 13
         fi

         log_completed "failed: post-swap health check failed; auto-rolled-back to $prev (service restarted on previous release)"
         echo "warning: new release failed health check; auto-rolled-back to $prev" >&2
         echo "         the broken release dir is preserved at $TARGET_DIR for inspection" >&2
         exit 12
       }
       ```

       Note: `atomic_swap` and `write_breadcrumb` are the same helpers used by the forward path. We deliberately reuse them so swap semantics are identical (UPDATE-06 `ln -sfn` only).

    3. **Recursion guard**: declare `IN_AUTO_ROLLBACK=0` near the top of the file (alongside `PARTIAL_RELEASE_DIR` and `TMPDIR_TO_CLEAN`). When the health check is invoked, gate it: `if [[ "${IN_AUTO_ROLLBACK:-0}" == "1" ]]; then return 0; fi`. Without this, an auto-rollback's `systemctl restart` would trigger another health check, which would trigger another rollback — an infinite loop on a host where the service is broken at the systemd-unit level (e.g. unit file syntax error introduced by a future Phase 11 change).

    4. **Replace the restart block in `cmd_install`** (currently the last few lines from Plan 10-02):

       ```
       if [[ "${SKIP_RESTART:-0}" == "1" ]]; then
         log_line "WARNING: SKIP_RESTART=1 — skipping systemctl restart AND post-swap health check"
         echo "warning: --skip-restart was passed; service has NOT been restarted." >&2
         echo "         the next invocation of this script will run a health check normally." >&2
       else
         if ! sudo systemctl restart vuln-reports.service; then
           log_line "ERROR: systemctl restart returned non-zero; running auto-rollback"
           auto_rollback "$PREV"
         fi

         if ! health_check; then
           log_line "ERROR: post-swap health check failed (systemctl is-active != active); running auto-rollback"
           auto_rollback "$PREV"
         fi
       fi

       # Rollback one-liner (UPDATE-11) — single line, copy-paste-ready.
       echo
       echo "Rollback: sudo ${INSTALL_ROOT}/current/scripts/update_from_github.sh --rollback"

       rm -rf "$TMPDIR_TO_CLEAN"
       TMPDIR_TO_CLEAN=""

       log_completed "success"
       ```

       Key invariants:
       - `auto_rollback` never returns to its caller — it always exits (12 or 13). So the control flow after `auto_rollback "$PREV"` is unreachable; this is intentional.
       - The rollback one-liner uses `${INSTALL_ROOT}/current/` — after the upgrade, `current` resolves to the new release, so the one-liner points at the just-installed script. Operators don't need to remember the version.
       - The blank `echo` before the rollback line gives visual separation from any pip / systemd output that preceded it. The one-liner itself is exactly one line.

    5. **Update `cmd_install`'s exit-code comment block** to document codes 12–15 (15 belongs to Task 2 but document it here too — both tasks edit the same file and the exit-code table is the canonical reference).

    1. **`cmd_rollback()` body**:

       ```
       local last_file="${INSTALL_ROOT}/releases/.last"

       # UPDATE-03: refuse if no breadcrumb history.
       if [[ ! -f "$last_file" ]]; then
         log_completed "failed: $last_file does not exist (no rollback history — use --list and --version to recover by hand)"
         echo "error: no rollback history; nothing to roll back to" >&2
         echo "       run --list to see installed releases and --version vX.Y.Z to switch to one" >&2
         exit 14
       fi

       local target
       target="$(cat "$last_file" 2>/dev/null || true)"
       if [[ -z "$target" ]]; then
         log_completed "failed: $last_file is empty"
         exit 14
       fi

       if [[ ! -d "$target" ]]; then
         log_completed "failed: $last_file points to $target which does not exist"
         echo "error: rollback target $target no longer exists" >&2
         exit 14
       fi

       # Sanity: target must be inside releases/.
       case "$target" in
         "${INSTALL_ROOT}/releases/"*) ;;
         *)
           log_completed "failed: $last_file points to $target which is outside ${INSTALL_ROOT}/releases/"
           exit 14
           ;;
       esac

       # Capture the current target so we can rewrite .last to it after the swap (UPDATE-07 shape:
       # the breadcrumb always reflects "what current pointed at before the most recent successful
       # swap", whether the swap was forward or backward).
       local prev_current
       prev_current="$(readlink "${INSTALL_ROOT}/current")"
       case "$prev_current" in
         /*) ;;
         *)  prev_current="${INSTALL_ROOT}/${prev_current}";;
       esac

       # Reuse the helpers from Plan 10-02 — same atomic-swap semantics.
       if ! atomic_swap "$target"; then
         log_completed "failed: atomic swap to $target during --rollback"
         exit 15
       fi

       write_breadcrumb "$prev_current"

       if [[ "${SKIP_RESTART:-0}" == "1" ]]; then
         log_line "WARNING: SKIP_RESTART=1 during --rollback — skipping systemctl restart"
         echo "warning: --skip-restart passed; service has NOT been restarted." >&2
       else
         if ! sudo systemctl restart vuln-reports.service; then
           log_completed "failed: systemctl restart after --rollback swap (current is now $target; service may be down)"
           exit 15
         fi
       fi

       echo "rolled back: current → $target"
       log_completed "success"
       ```

       Notes:
       - `--rollback` deliberately does NOT run the post-swap health check from Task 1. Rationale: the rollback target is, by definition, a release the operator previously trusted (it was running before the upgrade). If the health check fails on rollback, there is no further rollback target — `auto_rollback` would have nowhere to go. The operator-facing behavior is "rollback restarts the service; if the service is still broken, the operator escalates by hand." This is a deliberate scope decision aligned with UPDATE-03's text.
       - `--rollback` honors `--skip-restart` symmetrically with `--version` — useful for staged maintenance windows where the operator wants to swap the symlink during a quiet window and restart manually later.
       - `--force` has no meaning for `--rollback`. If both `--force` and `--rollback` are passed, Plan 10-01's parser should reject it as a usage error (it already rejects `--force` without `--version`; verify the existing check covers this case — if not, add it).

This subsumes the `--force --rollback` case. Confirm with a grep — if the existing check is `CMD != install`, it already covers rollback. Otherwise, tighten the check.

Refuses if no breadcrumb exists. Does NOT run the post-swap health check — the rollback target is by definition the previously-trusted release."

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `cmd_rollback` → `.last` breadcrumb file | The file is operator-writable (it lives under `/opt/vuln-reporting/releases/` which is root-owned in the v1.2 deploy model). A tampered `.last` could re-point `current` arbitrarily. We mitigate via the `releases/`-prefix check in `cmd_rollback`. |
| Auto-rollback → previous release | The previous release is whatever `current` pointed at before the upgrade — a release the operator previously trusted. We do not re-validate it (no second dry-run); the assumption is that a release that ran fine before will run fine again. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-12 | Tampering | `.last` rewritten by an attacker to point at `/etc/` or another sensitive path | mitigate | `cmd_rollback` rejects targets outside `${INSTALL_ROOT}/releases/` (case-glob check). |
| T-10-13 | Denial of Service | Auto-rollback infinite loop on a host with a systemd unit that always fails to come up | mitigate | `IN_AUTO_ROLLBACK=1` recursion guard short-circuits the health check on the rollback path. The script exits with code 12 or 13 and leaves the operator to investigate. |
| T-10-14 | Repudiation | Operator runs `--rollback` and there is no record of which release was rolled away from | mitigate | `log_line` records the rollback target; `log_completed success` confirms completion; the displaced target is captured in `.last` after the rollback so a "double-rollback" still has audit trail. |
| T-10-15 | Denial of Service | `--rollback` invoked when `.last` is missing and operator has no idea what to do | mitigate | Stderr message explicitly directs operator to `--list` + `--version` flow. Exit code 14 is distinct from other failures. |
