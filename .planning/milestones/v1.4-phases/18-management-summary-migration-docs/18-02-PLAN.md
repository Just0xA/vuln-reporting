gate (D-18-06, D-18-10 gate 1). The retention finding (30-day "wall" was an API

fixed-data consumer that previously relied on the implicit 30-day default. This

RESULT-CONSUMING callers with a precisely-scoped sweep (review changes #3 & #6) —

rolling-30), then widens the fetch only after the no-drift assertions are GREEN.

(CONTEXT specifics). The audit is a hard gate, not cleanup. Reconstruction
(Plan 03) depends on the widened fetch, so this gate must be GREEN first. The
live-API probe de-risks assumption A2 BEFORE Python logic is built on it
(Tenable export schemas are finicky; the ref doc can lag strict validation) and
verifies the CORRECT count direction — a wider lookback returns MORE rows, not
fewer (review HIGH change #3 corrects the prior filtered<default assertion).
Output: live-verified filter shape + correct-direction proof + bounded fetch +
config constant + precisely-scoped dynamically-complete consumer-audit suite.
</objective>
