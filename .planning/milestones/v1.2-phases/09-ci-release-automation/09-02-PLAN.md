<objective>
Insert a tarball-content assertion step into `.github/workflows/release.yml` (at the marker comment placed by Plan 09-01) that extracts the built tarball and fails the workflow if forbidden paths or non-placeholder credential values are present. This is the runtime safety net for CI-06 and the only guarantee against `.gitattributes` drift between releases.

Purpose: `.gitattributes` defines the slim-tarball boundary, but a future commit could accidentally remove an `export-ignore` rule, add a new sensitive path that wasn't anticipated, or commit an `.env` file. This step catches those failures at release time — before the tarball reaches operators — instead of after.

Output: A single new step in `.github/workflows/release.yml` (replacing the `# Tarball-content assertion step inserted by Plan 09-02` placeholder comment). No new files.
</objective>

<!-- Sourced from .env.example (committed file that ships in the tarball). -->

From `.env.example` (lines 5-6, 20):
```
TVM_ACCESS_KEY=your_access_key_here
TVM_SECRET_KEY=your_secret_key_here
SMTP_PASSWORD=your_smtp_password
```

Whitelist semantics:
- A line matching `^TVM_ACCESS_KEY=your_access_key_here\s*$` (with or without trailing whitespace/comments) is ALLOWED.
- A line matching `^TVM_ACCESS_KEY=` with any OTHER value is a FAIL.
- Same pattern for `TVM_SECRET_KEY` and `SMTP_PASSWORD`.
- `SMTP_USERNAME`, `SMTP_FROM_ADDRESS`, etc., are NOT credential fields per CLAUDE.md "Credential Management" and are NOT scanned (they may legitimately contain real-looking addresses in `.env.example`).

Forbidden top-level path list (any of these inside the extracted tarball is a FAIL):
- `.planning/`, `.env` (file, not directory), `.env.local`, `data/trend/`, `.git/`, `tests/`, `docs/`, `ref/`, `CLAUDE.md`, `RUNBOOK.md`, `CONTRIBUTING.md`, `.github/`

The tarball top-level entry is the prefix `vuln-reporting-${VERSION}/`, so checks are relative to that root after extraction.

Workflow shape from Plan 09-01 (insertion landing site):

    Replace the `# Tarball-content assertion step inserted by Plan 09-02` marker (placed by Plan 09-01) with a new workflow step named `Assert tarball contents`. The step uses `run:` with a multi-line bash block (`bash` is the default shell on `ubuntu-latest`; do not set `shell:` explicitly).

    Step shape (directive, not literal — implement in YAML/bash following CLAUDE.md):

    1. **Step name**: `Assert tarball contents`.

    2. **Step `run:` block** (bash with `set -euo pipefail` at the top):

       a. Resolve `VERSION="${{ steps.version.outputs.version }}"` and `TARBALL="vuln-reporting-${VERSION}-slim.tar.gz"`. Assert the tarball file exists; exit 1 with `echo "FAIL: tarball $TARBALL not found"` if not.

       b. Create a fresh temp dir: `EXTRACT_DIR=$(mktemp -d)` and `tar -xzf "$TARBALL" -C "$EXTRACT_DIR"`. The extracted top-level dir is `${EXTRACT_DIR}/vuln-reporting-${VERSION}`. Set `ROOT="${EXTRACT_DIR}/vuln-reporting-${VERSION}"` and assert it is a directory.

       c. **Forbidden-path check.** Declare a bash array `FORBIDDEN=( ".planning" ".env" ".env.local" "data/trend" ".git" "tests" "docs" "ref" "CLAUDE.md" "RUNBOOK.md" "CONTRIBUTING.md" ".github" )`. Initialize `FOUND=()`. For each entry, test `[[ -e "$ROOT/$entry" ]]`; if true, append to `FOUND` and `echo "FAIL: forbidden path present: $entry"`. After the loop, if `${#FOUND[@]} -gt 0`, exit 1. Print each finding with its type (`file` vs `directory`) via `stat` or `[[ -d ]]` test so the workflow log clearly explains the failure.

       d. **Credential scan.** Walk all files under `$ROOT` with `find "$ROOT" -type f -print0`. For each file, pipe through `grep -HnE '^(TVM_ACCESS_KEY|TVM_SECRET_KEY|SMTP_PASSWORD)='`. The `grep -Hn` line shape is `<path>:<lineno>:<VARNAME>=<value>`. Path elements may legitimately contain `:` (Windows drive letters, URLs in comments), so do NOT slice with `awk -F:` — the literal `awk -F: '{print $3}'` example given in earlier plan drafts is incorrect because $3 yields `VARNAME=value`, not the bare value. Use one of two unambiguous extractions: (a) `sed -E 's/^[^:]+:[0-9]+://'` to strip the `path:lineno:` prefix, then `cut -d= -f2-` to isolate the value, OR (b) match the line with a regex capture `^[^:]+:[0-9]+:(TVM_ACCESS_KEY|TVM_SECRET_KEY|SMTP_PASSWORD)=(.*)$` and compare capture group 2 against the placeholder. The comparison is **value-only** (the bare RHS, not the full `VARNAME=value` form). Then:
          - For `TVM_ACCESS_KEY=...`: PASS iff the bare value equals `your_access_key_here` (allow optional trailing whitespace and `#` comment).
          - For `TVM_SECRET_KEY=...`: PASS iff value equals `your_secret_key_here`.
          - For `SMTP_PASSWORD=...`: PASS iff value equals `your_smtp_password`.
          - Anything else → FAIL: print the file path and line number (`grep -Hn` output) and append to a `LEAK=` accumulator.
       Note: the matcher is anchored to the start of a line (`^`) so commented-out lines or in-prose mentions of these variable names do NOT trigger a false positive. The check tolerates blank `.env.example`-style lines like `# TVM_ACCESS_KEY=...` because those don't match `^TVM_ACCESS_KEY=`.

       e. **Final disposition.** If either `FOUND` or `LEAK` is non-empty, `exit 1` with a summary line `echo "ASSERTION FAILED: ${#FOUND[@]} forbidden path(s), ${#LEAK[@]} credential leak(s)"`. Otherwise `echo "Tarball assertion passed: no forbidden paths, no credential leaks"` and exit 0.

       f. **Cleanup**: not required — the runner is ephemeral; `mktemp -d` content is discarded with the VM. Do NOT add `trap rm -rf "$EXTRACT_DIR"` — it adds noise and the runner handles it.

    3. **Step position**: between `Compute SHA256 sidecar` and `Upload to GitHub Release`. The marker comment from Plan 09-01 is replaced wholesale — do not leave the marker behind.

    Implementation rules:
    - Use `set -euo pipefail` so any sub-command failure (including a `grep` returning 1 for "no matches" — which is the SUCCESS case for the credential scan) is handled correctly. The credential scan's `grep` must be guarded: `grep ... || true` for the "no match = good" case, then make the leak decision via the accumulator instead of grep's exit code.
    - Quote all path expansions (`"$ROOT"`, `"$entry"`).
    - Match the existing YAML indentation in `.github/workflows/release.yml` (2-space).
    - Do NOT extend the `forbidden` list to include `.gitattributes` or `.gitignore` — Phase 7 confirms those are stripped by their own `export-ignore` rules, and an assertion failure on them would conflate "this gate failed" with "Phase 7 boundary is broken". If Phase 7's boundary truly breaks, the broader `.planning/` / `tests/` checks will catch it first.
    - Do NOT add a check for `scripts/setup_github_labels.py` or `scripts/smoke_*` — those are explicitly named in `.gitattributes` and out-of-scope for the v1.2 credential-leak threat model.
    - Do NOT touch any source files or Phase 7 artifacts in this task.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Built tarball → release consumers | Operators receive whatever this workflow uploads. The assertion is the last gate before publish. |
| `.gitattributes` config → actual archive contents | Drift between intent and reality is the failure mode this plan exists to catch. |
| `.env.example` placeholder strings → real credentials | The whitelist must be tight enough that any real-looking value fails the build. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-05 | Information Disclosure | `.env` accidentally committed and shipped | mitigate | Forbidden-path check fails the build on `.env` or `.env.local` at the tarball root or any subpath. |
| T-09-06 | Information Disclosure | `.env.example` whitelist too loose, ships a real key | mitigate | Whitelist uses exact-string equality against the three known placeholder values, not a regex range. Any other value on a `TVM_ACCESS_KEY=` / `TVM_SECRET_KEY=` / `SMTP_PASSWORD=` line fails the build. |
| T-09-07 | Tampering | `.gitattributes` `export-ignore` rule silently removed in a future commit | mitigate | Forbidden-path check verifies the canonical Phase 7 exclusions are still effective regardless of `.gitattributes` state. |
| T-09-08 | Repudiation | Assertion failure without actionable detail | mitigate | Every failure prints the specific path and (for credential leaks) the file + line number to the workflow log. |
</threat_model>
