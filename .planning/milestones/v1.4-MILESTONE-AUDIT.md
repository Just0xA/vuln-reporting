## Re-Audit Addendum (2026-06-26)

A fresh `/gsd-audit-milestone` run re-verified the closure against the live codebase. All six phase VERIFICATION.md files report `passed`; REQUIREMENTS.md traceability shows 17/17 Complete; an independent cross-phase integration recheck (gsd-integration-checker) confirmed **25/25 exports wired, 0 orphaned, 0 broken E2E flows** — the prior "27/27 wired, 0 broken flows" claim is substantially correct.

**One new warning surfaced (REAUDIT-WARN-1) — not a closure blocker:**

The Phase 19 INT-WARN-1 fix (full-field `capture_snapshot()` forward-write in `reports/management_summary.py`) is **incomplete for 2 of 8 aggregate fields**. `_MGMT_MODULE_CONFIGS` (L86-94) composes 7 modules, but `reopened_count` is sourced from the `reopened_vulns` module (L492) and `sla_rate_crit_high` from the `program_health` module (L522) — **neither module is in `_MGMT_MODULE_CONFIGS`**. `_safe_metric()` returns `None` for both, so every `management_summary` snapshot write persists `reopened_count=None` and `sla_rate_crit_high=None`. The INT-WARN-1 regression test (`test_management_summary.py:1073`) asserts kwarg **key presence only**, not value non-nullness — it passes green over the nulls. This directly qualifies the `resolved_by_phase_19` claim that INT-WARN-1 "no longer nulls sla_rate_crit_high."

**Impact:** fail-soft, non-crashing. The cron writer (`scripts/capture_trend_snapshot.py`) computes both fields correctly. For any live month where `management_summary` writes the snapshot last, `program_health`'s SLA-posture MoM signal degrades to `missing` (OD-5 Amber cap) and reopened MoM context is absent — a graceful QUAL-01 degrade, not a break. **All 17 requirements remain satisfied; no FAIL-gate trigger.**

**Recommended follow-up (v1.5 cleanup or quick-task):** either add `reopened_vulns` + `program_health` to `_MGMT_MODULE_CONFIGS`, or drop the two un-sourceable fields from the `management_summary` writer and document `capture_trend_snapshot.py` as the canonical full-field writer — and strengthen the INT-WARN-1 test to assert non-None values.

**✅ RESOLVED 2026-06-26** — quick task `260626-elj` (commits `1276ccb` + `4407a6a`). Fixed via a third, cleaner approach: **inline compute**. `reopened_count` and `sla_rate_crit_high` are now computed directly in the `management_summary` snapshot block from `vulns_df`, mirroring the canonical cron writer (`scripts/capture_trend_snapshot.py`) — `reopened_count` via the REOPENED-state count (fail-soft `None` on missing `state` column), `sla_rate_crit_high` via `open_findings_at` + the shared D-05 `compute_sla_rate_crit_high` helper (fail-soft `None`). `_MGMT_MODULE_CONFIGS` (the 7 rendered modules) was left untouched, so the audience-facing report is byte-identical — this avoided the report-content change and baseline churn the "add modules" option would have caused. The INT-WARN-1 guard was strengthened (`test_reopened_and_sla_rate_forwarded_non_none`) to assert NON-`None` values (RED pre-fix / GREEN post-fix). Full `tests/test_management_summary.py` 17/17 pass (structural smoke + value-golden parity unchanged); `run_all.py --dry-run` validates all 5 groups.
